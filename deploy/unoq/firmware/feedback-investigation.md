# UNO Q 舵机反馈丢帧排查

2026-11-24，WonderDuck UNO Q 实机。主动推送试验采用 STM32 定时读取 15 个舵机和机身 IMU（ID 200），通过 Arduino Router 向 Linux 推送。每次完整的舵机总线回复为 16 × 18 = 288 字节。舵机总线 USART3 使用 1 Mbaud，Linux 和 STM32 间的 UART 使用 2 Mbaud。ToF 与头部 IMU 轮询已禁用。

## 已有结果

## Linux 串口抓取

在绕过 STM32 发送缓冲的固件上，用 `strace` 仅跟踪 Arduino Router 对 `/dev/ttyHS1` 的系统调用。Linux 两次都只收到一条 329 字节推送的前 85 字节，随后直接收到下一条完整推送。被截断的序号为 23 与 36。截断位置的最后一个字节与正常反馈不一致。序号 23 前紧邻一个有效的 13 字节舵机 RPC 回复。

| 同一固件的对照 | 结果 |
| --- | --- |
| 60 Hz 推送 + 约 50 Hz 简单 `echo`，12 秒 | 734/734 次舵机扫描长度完整，无坏帧或 RPC 超时。主机 579 次读反馈有 9 次没在期限内拿到数据，复用 1 次。 |
| 60 Hz 推送 + 约 50 Hz 舵机只读 RPC，4 秒窗口 | 253/253 次扫描长度完整，无坏帧，主机 196 次读反馈有 1 次不可用，UART 溢出计数保持 46。 |

Linux 驱动的 UART 接收溢出与复现同步发生。丢失的字节已在 Router 读取前缺失，Router 处理截断的 MessagePack 消息后失去边界，紧接着其他 RPC 也超时。历史 4.8% 中其他长度的样本仍缺少原始串口记录，尚不能都计入同一原因。

串口记录文件位于实机诊断目录，`tty-20261124-034753-2.trace` 是 echo 对照，`tty-20261124-034830-1.trace` 与 `tty-20261124-035158-1.trace` 包含截断。UART 溢出由 `ioctl(TIOCGICOUNT)` 的 `overrun` 字段统计。

## 推送消息间隔对照

在 `build-guard/` 保留轮询发送。上一个消息的最后一字节发送完成后，在 Arduino Bridge 的发送锁内插入 0.5 ms 或 1 ms 间隔。无间隔的 60 Hz 对照触发一次 UART 溢出。0.5 ms、100 Hz 窗口在序号 46 出错，溢出计数增加 2。1 ms、60 Hz 窗口在序号 14 出错，溢出计数也增加 2。三组均叠加约 50 Hz 的舵机只读 RPC，均因超时提前结束。

## 分离采样与推送的对照

在 `build-pull/` 固件中，STM32 继续以 100 Hz 扫描舵机总线，Linux 用 `feedback` RPC 以 50 Hz 获取缓存，同一轮还尝试读取 ID 20 扭矩寄存器。关闭主动推送时，45 秒内 4,496 次扫描全部达到完整长度，2,248 次主机读取均通过校验，额外读取无异常，UART 溢出计数保持 48。取缓存的 RPC 往返耗时中位数为 7.58 ms，p95 为 8.52 ms。含额外读取的测试循环有 104 次越过目标周期，反馈年龄上界 p95 为 24.37 ms。此测量来自只读诊断程序，运动控制的周期指标需要在正式服务下另测。

同一诊断固件的 200 秒窗口中，19,982/19,982 次扫描长度完整，9,996 次主机读取均通过校验，额外读取无异常，UART 溢出计数保持 48。包含额外读取的测试循环有 179 次超过目标周期。RPC 往返 p95 为 8.40 ms，反馈年龄上界 p95 为 24.20 ms。结果保存在实机诊断目录的 `pull-100hz-200s.json`。

候选固件将按需读取作为反馈协议 2。STM32 保持 100 Hz 定时采样，Linux 通过 `feedback` 请求返回缓存、采样序号和年龄。桥接检查每个舵机块的 ID 和校验和，并把 RPC 往返用时加到年龄上。连续两次读到同一个序号时报告本次没有新反馈。配合协议 1 或不支持缓存的旧固件时，桥接走原同步读取。

候选固件用仓库的 `build.py` 编译并通过 ELF 检查。UNO Q 上桥接的 3 个单元测试通过。正常桥接程序通过真实虚拟串口处理了 45 秒内的 2,248 次只读请求，零坏帧、零额外读取异常，UART 溢出计数保持 53。虚拟串口读取 p95 为 10.35 ms，反馈年龄上界 p95 为 25.47 ms。关闭虚拟串口后验证 STM32 停止定时采样。

## 正式控制路径验证

在已刷写的候选固件上，通过 systemd 运行时覆盖启动候选桥接与 `robotd`。实机处于 `held`，无控制方、运动指令为零。200 秒内完成 10,000 个控制周期，零超期、零总线读取超时、零连续总线错误。UART 接收溢出计数保持 53，Router 与桥接日志均无解码错误、反馈丢弃或 RPC 超时。机身 IMU 保持 ready，陈旧读数计数增加 2，结束时连续陈旧计数为 0。结果位于实机诊断目录的 `live-feedback-results.json`。实机保留候选固件和运行时服务配置，静止验证尚未覆盖走动负载。

## 摔倒保护期间的控制超期

同一候选版本在 2026-11-24 04:14:03 UTC 触发摔倒保护。实机 `/run/robotd.log` 记录 ID 34 的位置 P 增益寄存器 21 连续回报 15，泄力阶段要求 4，恢复姿态阶段要求 12。两阶段分别有 15 次和 11 次写后校验失败。04:14:04.41 返回站立策略后，常态增益 15 校验通过。ID 34 拒绝临时值的具体原因仍待确认。

当前实现在控制循环内同步执行两次批量写入和两次批量读回。校验失败时，本轮跳过新阶段的目标写入，下一轮重试整组。这段时间动作应用有 27 次单独超过 20 ms，用时 32.48–43.10 ms，含 26 次失败和恢复常态增益的那次写入。摔倒窗口没有总线读取失败，桥接和 Router 也没有记录反馈丢弃、解码错误或 RPC 超时。

Studio 直接显示 `robotd` 的累计 `missed`。50 Hz 控制循环每次实际执行超过 20 ms 就加 1，统计的是超期的执行次数。摔倒前后的 27 条动作耗时记录能解释这一批增量，不能用累计值推算从摔倒到站起共停了多久。

## 行人检测切到 CPU 后复查

2026-11-24，STM32 实机返回反馈协议 2，采样序号为 0。Linux 安装的是旧桥接脚本，正在运行的 `robotd` 缺少 `WONDERDUCK_UNOQ_FEEDBACK=1`，控制反馈走同步读取。同步读取时，零运动指令下的 18.6 秒内累计超期增加 264 次，当时行人检测未运行。

恢复已验证的桥接脚本，并通过持久的 systemd 配置启用缓存读取后，STM32 采样序号在 0.3 秒内从 149 增至 179。零运动指令下，行人检测空闲和运行时各采样 18.6 秒，两次均新增 3 次超期，控制频率在 50 Hz 附近。运行行人检测时，检测进程保持在 CPU 0–2，CPU 3 继续供运动控制和串口桥接使用。这次采样覆盖静止工况。

随后将 `robotd.service` 的默认 CPU 亲和性扩大为 CPU 0–3，运动控制线程单独绑定在 CPU 3。在同一次行人检测订阅内，开放前 12.02 秒输出 7 帧，处理耗时中位数 1037 ms，新增控制超期 0 次。开放后 15.02 秒输出 23 帧，处理耗时中位数 642 ms，新增控制超期 3 次。两段的运动指令均为零，检测使用 ncnn CPU 双线程，STM32 缓存读取处于启用状态。

## 逐帧录制的扩展反馈

2026-11-27，UNO Q 的坐立策略逐帧录制走 HX 同步读取，每个设备从地址 40 读取 28 字节。常规 12 字节反馈的缓存开关无法覆盖这组寄存器。实机日志中，328 次读成功时已超过 20 ms 截止时间，另有一次 ID 200 超时。同板只读测量中，544 字节的空载 RPC 往返中位数为 9.50 ms，实际读取再返回同样大小的数据为 21.00 ms。两者相差约 11.5 ms，包含 STM32 串口采样与对应 RPC 的额外处理。

反馈协议 3 增加 28 字节缓存。STM32 以 16 ms 为目标采样周期，Linux 按需获取新样本。录制脚本在 UNO Q 虚拟串口上默认启用缓存，旧固件继续通过同步读取提供扩展反馈。

刷写后在控制服务停止、关节卸力的条件下，通过同一虚拟串口做 50 Hz 只读对照。每组剔除前五轮预热。

| 路径 | 轮数 | 中位数 | P95 | 超过 20 ms | 读失败 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 28 字节同步读 | 500 | 22.89 ms | 23.90 ms | 500 | 1 |
| 28 字节缓存读 | 2400 | 12.66 ms | 18.67 ms | 23 | 1 |
| 12 字节缓存读 | 250 | 10.41 ms | 11.16 ms | 0 | 0 |

扩展缓存样本年龄上界的 P95 为 28.70 ms。只读窗口未覆盖运动中的策略推理、舵机写入和姿态切换。

## Router RPC 与 CPU 唤醒延迟

实机 `/dev/ttyHS1` 配置为 2 Mbaud，8N1。空载 RPC 的请求与回包合计约 36 字节，理论串行传输耗时约 0.18 ms。Linux Router 本地方法的往返中位数为 0.91 ms，同批测试中 STM32 空载 RPC 为 3.30 ms，552 字节回包为 8.16 ms。

将 STM32 RouterBridge 的空闲轮询等待从 1 ms 缩短至 250 µs，并在运动控制有效期间通过 Linux PM QoS 请求 100 µs 的 CPU 唤醒延迟上限。停止策略并退出运动状态时释放请求。录制程序在 UNO Q 端口上默认启用相同设置，扩展反馈 RPC 与常规反馈共用总线优先级。

| 配置 | 空载 RPC P95 | 552 字节 RPC P95 | 扩展缓存中位数 | 扩展缓存 P95 | 扩展缓存超期或失败 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 原轮询和原 CPU 设置 | 6.45 ms | 9.81 ms | 12.74 ms | 18.87 ms | 5 / 600 |
| 250 µs 轮询 | 5.48 ms | 9.19 ms | 12.29 ms | 18.36 ms | 2 / 600 |
| 250 µs 轮询和 100 µs CPU 唤醒延迟上限 | 2.57 ms | 5.97 ms | 8.53 ms | 13.99 ms | 0 / 600 |

实测为关节卸力、控制服务停止时的总线测试。临时 PM QoS 请求用于模拟运动期间的 CPU 设置。常规 12 字节缓存的 P95 从 11.21 ms 降至 6.73 ms，两组各 250 轮，无超期或读取失败。

## 逐帧录制的样本年龄校验

11 月 27 日 06:28 UTC 的实机录制记录了 100 次读取超期后成功和 39 次读取失败。24 次元数据过期均收到 558 字节，包括有效元数据和 16 个完整设备帧。桥接将 RPC 往返耗时加到 STM32 样本年龄后写入元数据，robotd 又从主机请求时刻开始累加耗时。06:28:52.057 的元数据年龄为 27.20 ms，主机读取耗时为 32.67 ms，按原公式得到约 59.87 ms，因超过 50 ms 被拒绝。桥接另有不完整帧告警，常见长度为 510 字节。

桥接继续使用 STM32 年龄与 RPC 耗时之和执行转发前的年龄检查，元数据字段携带 STM32 报告的年龄。robotd 从主机请求时刻算起，到读取结束时校验样本年龄上界。录制等待启动期间也会维持 CPU 唤醒延迟请求，频率下限仍由运动状态决定。失败日志优先显示本次读取结束时缺失的设备。

部署后，1000 轮 28 字节缓存只读测试的中位耗时为 8.55 ms，P95 为 13.93 ms，最大值为 15.42 ms，均在 20 ms 内完成。250 轮常规 12 字节缓存测试也全部成功。动态录制仍待实机复测。

## ToF 与 Router 锁竞争

2026-11-27，在策略开启且未发出行走指令时，`/proc/locks` 捕获到 ToF 进程持有共用的 `wire` 锁，运动反馈桥接进程等待同一把锁。保持同一固件和策略，交替运行与暂停 ToF。每组约 12 秒，暂停两组结束后恢复采集。

## 机身 IMU 样本年龄的计算

STM32 在开始扫描 15 个舵机和 ID 200 时记录整组时间戳，处理取缓存请求时才计算该时间戳的年龄。ID 200 在正常扫描顺序的末尾。这段年龄覆盖整组扫描和缓存等待。旧版 Linux 再加上从发出反馈请求到策略推理的用时。Linux 请求先于 STM32 计算年龄，两段时间在请求发出到 STM32 计算年龄之间重叠，因此旧日志值是以整组扫描起点推算的保守上界。当前常规反馈包缺少 ID 200 内部采样时间和融合序号。

按 Linux 桥接转发的序号对齐 `production-tof-5hz-20261127.json` 的分段数据与同一时间的 `/run/robotd.log`。这三个窗口早于禁用 ToF，247 条告警均成功对齐。STM32 报告年龄的中位数为 15.07 ms，Linux 从请求到推理为 8.00 ms，日志年龄为 23.10 ms。Router RPC 中位数为 4.13 ms，Linux 从 Router 收到回复到开始推理为 0.76 ms。

STM32 的年龄计算时刻位于 Router 的 RPC 起止时刻之间，据此可以给每条告警计算整组扫描起点到推理的年龄区间。247 条中有 109 条的区间上限在 20 ms 以内，2 条的区间下限超过 20 ms，其余 136 条的区间跨过 20 ms。整组扫描的区间仍无法定位 ID 200 内部的采样时刻。关闭 ToF 后的 212 条站立告警全部为 `over_age`，没有反馈复用，告警年龄中位数 22.53 ms，P95 为 25.20 ms。

Linux 桥接现随反馈提供与 `robotd` 共用时钟的 Router RPC 起止时刻。策略诊断从这两个时刻和 MCU 报告年龄推算整组扫描的年龄区间。区间下限超过控制周期才产生超龄告警，取值区间写入诊断数据。同一帧再次使用仍由反馈序号检查。总线接收沿用独立的 50 ms 保守年龄校验。

新版本部署后，在 15 个主关节卸力的条件下以 50 Hz 对照同一批帧。统计截止于主机读完反馈，策略推理时间另计。

| --- | ---: | ---: | ---: | ---: | ---: |
